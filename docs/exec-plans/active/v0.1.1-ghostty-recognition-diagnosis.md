# Ghostty recognition diagnosis

2026-10-04 read-only investigation, based on root `641f24b`. No terminal UI,
AppleScript, synthetic GUI input, real source task, source configuration change,
credential, session body, or transcript read was used.

## Confirmed layers

- The default Hermes AIsland ownership manifest points to the `setup-fixed`
  case callback. Its owned wrapper exports that case's `bridge.sock`, then
  executes that case's packaged `OpenIslandHooks`. The newly built `runtime-live`
  case is a different address. A socket file's existence does not establish that
  an App is currently listening.
- Claude and Codex ownership manifests still point to the normal managed
  Application Support callback. The source-setup acceptance allowlist intentionally
  migrates only Hermes, DeepSeek Desktop and MiniMaxCode Desktop; other workstreams'
  callbacks are preserved. Their absence from this isolated App cannot establish
  a Ghostty-specific failure.
- The exact Ghostty executable has a shell descendant family with a normal
  `ttys000` TTY. Only PID/parent PID/TTY/executable-name/start-time metadata was
  inspected. Python/bun executable names alone do not identify the user's agent.
- `HermesHookAdapter` reuses authoritative `TERM_PROGRAM` host classification:
  `ghostty` becomes `Ghostty`. Its locator provider deliberately returns nil,
  so Hermes does not inspect a focused Ghostty window. TTY is retained; a missing
  terminal window UUID is not a lifecycle-admission requirement.
- `RuntimeLifecycleReducer` validates lifecycle identity independently of optional
  terminal metadata. `BridgeServer.processRuntimeLifecycleHook` has no Ghostty
  exclusion. The acceptance App disables historical and process discovery in
  `AppModel.startIfNeeded` and `applyStartupDiscoveryPayload`; it relies on new
  hooks, rather than discovering all pre-existing terminal processes.
- The case lifecycle registry was projected only to Hermes source/terminal label,
  TTY/window-ID presence, coarse event and counts. It contained Terminal and
  Unknown entries, but no Ghostty-labeled entry. This establishes only that no
  Ghostty-labeled lifecycle event is recorded, not that a user's Ghostty agent
  emitted an event which was dropped.

## Source-supported remaining hypothesis

Public Hermes `hermes_cli/main.py` loads configuration and calls
`agent.shell_hooks.register_from_config` at CLI startup. `shell_hooks.py` stores a
`ShellHookSpec.command` in the callback closure; `_spawn` executes that command.
Rewriting the YAML on disk does not by itself replace a running process's
registered callback. An older process can continue using a previous callback, or
have no registered hook if normal source consent was not accepted at startup.
This mechanism is confirmed by source; the particular command held by an
existing user Ghostty process has not been read or established.

## Deterministic ingress check

`GhosttyHermesIngressTests` starts only a temporary `BridgeServer`, runs the actual
repository callback executable with synthetic Hermes stdin and a minimal fixed
environment, and observes real bridge events. Two Ghostty TTYs and one Terminal
TTY must remain distinct, reach completed/succeeded state, and retain the Ghostty
label without window IDs. It does not launch Hermes or query/control Ghostty.
The test requires `AISLAND_TEST_HOOKS_BINARY` to identify the compiled callback.

## Follow-up: confirmed Oh My Pi callback route

Read-only first-two-entry classification of the exact Ghostty process family
matched the installed Oh My Pi executable/script marker. Its TTY-attached entry
started at 08:05:44Z. A second matched entry was TTY-less; the separate Python
entry remains unclassified. All later arguments, environments and terminal
contents were excluded. These observations do not establish a Ghostty Hermes
process or a particular cached Hermes command.

The Oh My Pi version 3 ownership manifest points exactly to the regular managed
extension. Its file has the production-default-or-inherited socket declaration,
last modified 2026-09-29, with no `runtime-live` literal. The installed file equals
the reviewed bundled template after substituting `oh-my-pi`. Meanwhile the
default Hermes manifest has been migrated to `runtime-live`. Thus the confirmed
Ghostty source has a callback routing gap in the isolated App.

`PiExtensionInstallationManager` now accepts explicit `targetSocketURL` on
`status` and `install`. The default retains the existing production socket
behavior; an explicit target replaces only the reviewed socket declaration with
a literal which takes precedence over inherited environment. Version 4 records
the rendered file SHA-256 and target. Old version 3 migration requires exact
reviewed production-template bytes; version 4 requires a matching owned receipt
hash. Foreign, modified and symlink entries are refused. Migration saves both
old extension and manifest in private `connection-backups/aisland-pi-*`; repeats
are idempotent. Legacy removal can supply `extensionSourceData` for the same
exact-template proof. The coordinator still owns cancellation intent and must
pass the target to both status and install; this manager does not auto-run setup.

The public installed Oh My Pi `loader.d.ts` documents that the root session
imports extension paths once and child sessions reuse the prepared module graph.
The managed callback's socket is a module-level constant. A file update alone
does not prove an already-running source changed its route; normal source reload
or restart and a new real turn remain necessary acceptance checks.

Targeted fixture log: `output/verification/v0.1.1-omp-socket-migration/`.
No real extension was changed or source task launched in this implementation.

## 2026-10-04 real feedback and expanded verification

The user confirmed Hermes in Ghostty appeared as completed and clicking returned
to the same conversation (build 45). This is Hermes evidence, not acceptance of
all Ghostty agents. A fresh Oh My Pi turn subsequently appeared in build 46 but
the user reported its click selected another Ghostty page. Grok Build produced
no card in either Terminal.app or Ghostty.

Read-only configuration inspection found no Grok managed hook or ownership
manifest. The isolated build 46 source allowlist contained only Hermes, DeepSeek,
MiniMaxCode and Oh My Pi, and disabled ordinary session/process discovery. It
cannot serve as the complete supported-agent compatibility test. A normal
`dev.aisland.app` bundle is now being prepared with ordinary detection, installers,
discovery and listeners. Existing preferences and exact managed configurations
are privately backed up before switching runtimes.

The Oh My Pi route exposed a separate precision fault: its extension did not
capture a Ghostty surface ID, and jump-back selected the first page sharing a
working directory. The revised extension captures an ID only on an actual
interactive source input (or unambiguous startup); background tool/stop/heartbeat
events reuse the captured ID. Fake Pi/OMP instances sharing a directory remain
bound separately. Exact jump ID misses no longer fall back to another page;
directory or exact-title fallback requires an unambiguous inventory match, and
the focus response must equal the selected ID.

The coordinator now compares installed Pi/OMP bytes with the current bundled
template, in both normal and isolated status refreshes. Ownership of an older
template is no longer treated as current. Explicit user removal still prevents
automatic reinstallation. Root integration checks passed 32 tests across five
suites; log `output/verification/v0.1.1-approved-r9-r8-audio/ghostty-connection-integration-tests.log`.
These tests use fixtures; the new multi-page click behavior still requires real
user verification. Remaining ordinary background locator/reconciliation paths
are under review before declaring all supported Ghostty agents repaired.
