# MiniMax Desktop normal-mode stability

Base: `7e89e53`. This work uses synthetic SQLite/runtime fixtures and source inspection only; no source GUI, real conversation database or user configuration is changed.

## Confirmed normal-mode removal cause

`RuntimeLifecycleReducer` emits live sessions keyed by source, profile and native session ID. `SessionState.apply(sessionStarted)` marks them hook-managed. Normal `ProcessMonitoringCoordinator.reconcileSessionAttachments` computes alive IDs, calls `markProcessLiveness`, then `removeInvisibleSessions`. The alive-ID method included DeepSeek Desktop but omitted MiniMax Desktop. Therefore two normal missing-process polls set `isSessionEnded` and remove an otherwise valid MiniMax card. The passive Desktop utility process has no CLI TTY. Prior acceptance mode did not run this normal polling path, so a single verified completion/navigation did not cover this failure.

The fix checks currently running `com.minimax.agent` applications and their public bundle version, then retains every independently admitted MiniMax Desktop native session. The Core policy requires matching namespaced native identity, profile, metadata DB path and reviewed source version. Workspace and process PID are not deduplication keys. Explicitly ended sessions remain ended; an absent/unsupported app still follows the existing two-poll expiry. DeepSeek behavior is unchanged.

## Evidence boundaries

Synthetic tests cover two native conversations in one workspace, repeated normal liveness polls, identity preservation, source exit/version mismatch and rejected/ended rows. Actual simultaneous source conversations, overlay visibility and exact foreground navigation still require root's GUI verification. `JumpTarget` currently carries native conversation/profile/DB/version metadata, not a runtime PID; this round does not introduce a guessed PID or navigation fallback.

Verification: `python3 scripts/test-runtime-lifecycle-isolated.py` passed 26 tests in 4 suites, including 3 new liveness cases. `swift build --product OpenIslandApp` passed in 65.03 seconds (source executable compile only; no App bundle or launch). Logs are under `output/verification/v0.1.1-minimax-multi-session/` in this worktree.

## Confirmed subsequent terminal-first projection loss

The metadata monitor correctly projects a newly committed terminal with `sourceObservedStart=false` when it never observed accepted state. However, the reducer previously rejected a different native turn ID whenever the session already had a cursor, or rejected all terminals after a finished cursor. Therefore a first terminal-first conversation could synchronize, while a later terminal-first turn in that same conversation vanished completely. A registry restored with an unobserved old running turn had the same problem.

Real synthetic SQLite→monitor→reducer tests reproduce these failures before the fix (29 checks run; the two new terminal-first cases record 12 failed expectations). The reducer now admits a new unseen MiniMax terminal only after an unobserved cursor, with reviewed metadata/version and nondecreasing time. An actually observed active turn still cannot be ended by a different ID. Seen turn IDs and timestamp/sequence guards remain effective. This synchronization emits a completed card with a silent completion; it creates no fake start or success notification. The real two-native-session fixture additionally verifies lifecycle independence and both identities after registry restoration and normal polling.

After-fix verification: all 29 tests in 4 suites pass; the incremental `OpenIslandApp` source build passes in 3.26 seconds. `terminal-first-before.log` records the failing regression; `terminal-first-after.log` and `app-source-after.log` record successful verification. No real source DB, GUI, credential, process argv/environment or user configuration was accessed by these tests.

The namespaced runtime reducer/monitor and `SessionState` use source/profile/native session IDs, not PID or cwd. Runtime registry writes retain both dictionary keys; the new restoration fixture verifies this. No source-supported native-ID coalescing cause was found. `JumpTarget` retains conversation/profile/database/version metadata through the lifecycle and registry fixtures. Actual click/foreground failures cannot be diagnosed from these Core checks alone; UI and attachment-resolution fixes remain owned by the main flow.
