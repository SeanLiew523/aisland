## 5. 建议的分层排查与验收

1. 先确认当前进程、受管 helper 和真实 hook/extension/socket route，使用正常模式；不要把验收 fixture 的独立 socket/profile 混入普通运行。
2. 对用户失败的具体会话，从 card identity 到 JumpTarget、只读 metadata lookup、源应用/窗口 admission、准确页选择、最终原生 ID 核对逐层追踪。闭词错误分类需要能区分异常原因；不能所有数据库错误都压成一个笼统 metadata-unavailable 再猜根因。
3. Ghostty 优先比较已通过的 Grok 与失败的 Claude/OMP/Hermes，覆盖同工作目录、多窗口、多 tab/split、从其他页/其他应用点击返回、既有进程与安装接入后的新进程。准确选择需要原生 surface/terminal 身份，不能兜底到 cwd/title/第一窗口，不能把弹出全部窗口算成功。保留 Terminal 对照。
4. ZCode 使用用户真实失败会话，区分独立任务/项目任务、重名/相近名称、空白草稿、另一个已打开会话；定位 metadata→sidebar→current menu ID→frontmost 的具体断点，保护剪贴板。测试样本的专用唯一标题不能代表用户普通标题都通过。
5. MiniMaxCode 被动接入既有会话，不主动创建来源会话。先定位本轮 metadata-unavailable 的确切 cause，核对活动数据目录/profile/native ID/DB 读法/缓存目标；至少用两个普通既有会话验证，覆盖同时完成、普通轮询不丢卡、切页、从后台点击、来源与 AIsland 重启。不放宽精确 ID 核对来获得“成功”。
6. 用实际失败材料形成有意义的 red 回归→修复→targeted green，再构建独立更高 build 的完整 bundle，并进行真实来源复测。最终验收逐项报告“可识别/正确状态/准确原页/正确前台”，不能将 fixtures 或激活当后两项。
7. 交付每轮包含明确版本/构建号、根因与证据、窄改动、测试范围/未覆盖项、提交；用户确认效果之后才扩大范围。不要复用“全部测试通过”的措辞掩盖真实未验收来源。
